# ResearcherConnect — Design Document

**Date:** 2026-07-24
**Project:** Prototype for the Organization Science "Call for Prototypes" submission
**Paper:** *"Nice to Meet You — Could My LLM Talk to Yours?" Identifying Latent Scientific Collaboration Opportunities through LLM-Mediated Conversations* (Ostern & Kowalkiewicz, draft)
**Authors of this prototype:** Marek Kowalkiewicz (built with Claude Code)

---

## 1. Purpose

A highly visual, local-first web application whose backend runs an **agentic system** that identifies **latent collaboration opportunities** among researchers. Two LLM agents — each representing a researcher's "mind" (expertise, interests, current goals) — hold a structured conversation on the researchers' behalf, attempt to construct a shared research problem, and produce an *opportunity brief*. The system then classifies each discovered opportunity against the four established tie-formation mechanisms (Dahlander & McFarland, 2013) to decide whether it is **structurally predictable** or **genuinely latent** — the paper's core empirical move.

### Definitions (from the paper)

- **Latent collaboration opportunity** — a potentially valuable basis for joint research that (a) has not yet developed into a social tie and (b) is unlikely to become visible through established tie-formation mechanisms alone. It is *constructed* through interaction, not retrieved by similarity matching.
- **Tie-formation predictors (the baseline):**
  1. **Organisational foci** — shared settings (school, faculty, projects)
  2. **Status & value homophily** — similar standing, beliefs, orientations
  3. **Cumulative advantage** — already well-connected researchers attract more ties
  4. **Triadic closure** — shared third-party contacts

### Success measures (from the email thread)

1. **Human–machine alignment** (Marek): do humans commit to / decline the opportunities the machine proposes? The app records accept/decline decisions per opportunity.
2. **Beyond-baseline discovery** (Nadine): can the LLM identify connections **not explainable by established predictors of tie formation**? The app computes the four predictors for every pair and classifies each discovered opportunity as *predicted* vs *latent*.

## 2. The five-step research design → five app views

The app's UI mirrors the paper's research design as a pipeline rail:

| Step | Paper | App view |
|---|---|---|
| 1 | **Baseline** — existing network graph + tie-formation predictors | Interactive force-directed network of researchers; solid edges = existing collaborations; per-pair predictor scores |
| 2 | **Representation** — researcher-verified LLM personas | "Research Minds" panel: persona cards generated by the Persona Agent from profile data; editable/verifiable by the researcher |
| 3 | **Conversation** — LLMs develop possible bases of joint work | Conversation Theater: watch two agents converse turn-by-turn (streamed live) |
| 4 | **Validation** — researchers assess the constructed opportunity | Opportunity cards with scores + Accept / Decline / Discuss buttons; decisions logged |
| 5 | **Comparison** — discovered connections vs baseline model | Dashboard: latent vs predicted opportunities, dashed glowing edges overlaid on the baseline graph |

### 3.1 The agentic pipeline (backend)

A **run** targets one researcher pair (or an auto-scan queues the top-K unconnected pairs ranked by *lowest* baseline predictability — deliberately probing where classical models predict nothing):

1. **Baseline** (`baseline.js`, deterministic JS — no LLM): compute the four predictor scores for the pair from the seed graph. Also produce a composite `structural_predictability` ∈ [0,1].
2. **Representation** (`agents/persona.js`): one LLM call per researcher → a persona spec (expertise map, methods, current questions, collaboration style, what they'd want from a collaborator). Cached per researcher; editable via the UI (the paper's "researcher verifies representation" step).
3. **Conversation** (`agents/conversation.js`): alternating turns, each turn = one LLM call carrying that persona's system prompt + transcript so far. 6 turns (3 each) by default. Structured phases nudged via the prompt: introduce → probe complementarity → co-construct a problem → sketch a study. Streamed to the browser via SSE.
4. **Synthesis** (`agents/synthesizer.js`): one LLM call over the transcript → opportunity brief as JSON: `{title, shared_problem, contributions: {a, b}, research_question, study_sketch, novelty (1–5), complementarity (1–5), feasibility (1–5), verdict}`.
5. **Comparison** (`agents/assessor.js` + `baseline.js`): the LLM explains the pair in tie-formation terms; combined with the deterministic scores → classification `predicted | borderline | latent`.
6. **Validation** (human): accept/decline/discuss recorded on the run record with a timestamp.

Every artifact (persona prompts, every message, model ID, provider, timestamps, scores, human decisions) is persisted to `data/runs/<run-id>.json` — the **provenance chain** Marek's email emphasises.

### 3.2 LLM provider abstraction

| Provider | When | Notes |
|---|---|---|
| `anthropic` | `ANTHROPIC_API_KEY` set | `@anthropic-ai/sdk`, model `claude-opus-4-8`, streaming, adaptive thinking |
| `claude-cli` | `claude` binary present (default on this machine) | spawns `claude -p --output-format json`; uses the local Claude Code subscription — zero config |
| `demo` | always available; forced with `PROVIDER=demo` | replays bundled pre-computed runs with realistic pacing — the app demos without any credentials |

Provider + model are recorded in every run's provenance.

### 3.3 Seed data

Ten fictional synthetic researcher profiles span distinct fields and a fictional collaboration graph. The distributed dataset lives in `server/data/researchers.json`; every persona is explicitly marked synthetic and none represents a real person.

### 3.4 Frontend

Single-page, vanilla ES modules. The network graph is the hero: custom canvas force simulation (~150 lines, no d3). Solid grey edges = existing ties; when a run completes, a discovered opportunity draws an animated dashed edge coloured by classification (latent = vivid accent, predicted = muted). Clicking a node shows the researcher card; clicking two nodes (or an edge suggestion) starts a run. The Conversation Theater slides in and streams the dialogue. The dashboard tab summarises: runs, accept-rate (alignment metric), latent-vs-predicted split (beyond-baseline metric).

Visual direction: decided at implementation time with the frontend-design and dataviz skills; intent is a distinctive "research observatory" look — dark canvas for the graph, precise typographic hierarchy, no template feel.

### 3.5 Error handling

- LLM failures: retry once, then mark the run `failed` with the error in provenance; UI shows the failed stage on the rail.
- CLI provider timeout: 120 s per call; killed and surfaced.
- No credentials at all: server boots in demo mode and says so in the UI header.

### 3.6 Testing

`node --test` covers the deterministic core: baseline metrics (triadic closure, homophily, foci, degree), classification thresholds, run persistence, and the full pipeline against the demo provider (no network needed). LLM-dependent behaviour is exercised via the demo driver.

## 4. Alternatives considered

1. **Streamlit (Python)** — fastest to build, matches TheBigFill/BudgetSmarts, but "highly visual" (custom network animation, streaming theater) fights Streamlit's rerun model. Rejected.
2. **Karpathy-loop clone (autoresearch-style evolutionary agent)** — closer to the original email idea, but the paper's design has since crystallised around pairwise persona conversations + baseline comparison; the evolutionary loop adds cost without serving the five steps. The conversation engine keeps a "human steering" affordance (the Discuss/feedback action) in that spirit.
3. **Chosen: vanilla web app + Node agentic backend** — matches workspace conventions, no build step, deployable to Netlify later (static front + functions) if needed, and gives full control of the visuals.

## 5. Out of scope (v1)

- Real QUT collaboration-graph ingestion: access and governance remain unresolved. Any future real edge list belongs only in a separate private study copy, never in the shared fictional seed or Git history.
- Multi-user auth, email ingestion of researcher "minds", automatic literature retrieval.
- Deployment (local-first; Netlify optional later).

## 5b. Addendum (post-exploration, same day)

After this document was drafted, a workspace scan located **SyncMinds v0.1** (`OrgSci/syncminds/`) — the "version 0.1" from the email thread: a Python/Streamlit prototype with layered persona mind files, a four-round pipeline, a `claude -p` provider, and a preserved provenance trail (the origin emails, the June 2026 meeting transcript, and the project plan). Consequences for this design, as built:

- The public demonstration dataset uses ten fictional synthetic personas; private experimental inputs are not distributed.
- The `claude-cli` provider follows SyncMinds' `ClaudeCLIProvider` pattern, ported to Node.
- The honest-failure case (Lena Fischer) and the audit-trail discipline carry over.
- ResearcherConnect is positioned as the **visual successor** to SyncMinds: pairwise conversations + baseline comparison (the paper's current framing) rather than SyncMinds' call-triggered team assembly. See ARCHITECTURE.md § "Relationship to SyncMinds v0.1".
- Visual direction, as implemented (after two design passes and owner feedback rejecting dark mode): "chart room" — an engraved star-atlas plate in indigo ink on pale chart paper. Planisphere grid, plate frame, diffraction-spike star glyphs, italic serif labels, chart stamps, meridian-scale pipeline rail, catalogue-ledger probe queue; classification palette CVD-validated against the light surface.
